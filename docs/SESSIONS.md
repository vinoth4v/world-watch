# Sessions

A log of what was asked, what changed, and what's still open — kept so the
reasoning behind a decision doesn't have to be reconstructed from the diff
later.

## 2026-08-08 — Initial alerts feature (issue #8)

**Asked:** update the README, include a world map image to show the alerts,
provide an option to filter by date.

**Found:** the repo was still the bare template scaffold — no `alerts` data
model, no map, homepage was the placeholder "Replace this page" screen. The
three asks only make sense together: there was nothing to show on a map or
filter by date until the underlying feature existed.

**Changed:**

- Added an `alerts` table (`apps/web/src/db/schema.ts`,
  `apps/web/src/db/migrations/0001_alerts.sql`) and a data access layer
  (`apps/web/src/db/alerts.ts`).
- Rebuilt the homepage (`apps/web/src/app/page.tsx`) around it: a GET-based
  date filter, an inline-SVG world map plotting alerts by lat/lng
  (`apps/web/src/app/world-map.tsx` +
  `apps/web/src/app/world-map-projection.ts` +
  `apps/web/src/app/world-map-continents.ts`), a plain list view, and a
  "Report an alert" form (`createAlertAction` in
  `apps/web/src/app/actions.ts`).
- Updated `README.md` to describe the app as it now is instead of the
  template placeholder.

**Decided:**

- **No new mapping dependency.** A hand-built equirectangular SVG plots
  alerts with zero new npm packages. `AGENTS.md`'s blessed-dependency list
  has nothing for 2D maps, and picking one (Leaflet vs. Mapbox GL vs.
  something else, several of which need an API key) is a dependency decision
  the rule says to raise explicitly, not fold into a feature PR. If real
  coastline accuracy or pan/zoom becomes a requirement, that's the trigger to
  raise it.
- **Continent outlines are hand-simplified, not sourced geodata.** Same
  reasoning in miniature: pulling in a real geodata file (Natural Earth,
  TopoJSON, etc.) is itself a small dependency/licensing decision. The
  low-poly outlines in `world-map-continents.ts` are recognisable, not
  precise — good enough to place markers meaningfully, not good enough for
  anything that needs exact coastlines.
- **No ingestion pipeline.** The issue asked to show alerts and filter them,
  not to pick a live data source. Given there wasn't one already, alerts are
  entered by the operator through a form. Building automated ingestion means
  choosing an external API (which one, what it costs, what secrets it needs)
  — a decision for a human, not something to default into quietly.
- **Filter is a plain GET form, no client JavaScript.** Consistent with the
  rest of the template (the sign-in form works the same way): no route
  handler, no client component, works with JS off, and the filtered view is
  a shareable URL.
- **Severity, not the date filter, drives marker colour**, reusing the three
  semantic tokens the design system already has (`success`/`accent`/
  `danger`) rather than adding new ones for a fourth "critical" hue —
  `high` and `critical` share `danger`.

**Rejected:**

- A live/scheduled data feed — no source was specified, and picking one
  unilaterally would mean shipping a dependency and possibly a secret
  without the sign-off `AGENTS.md` requires.
- A full admin UI for editing/deleting alerts — out of scope for "show
  alerts on a map with a date filter"; the create-only form is the minimum
  needed to make the feature demonstrably work.

**Still open:**

- No automated ingestion — someone has to decide the data source before that
  can happen.
- No edit/delete for a mis-entered alert; only inserts exist today.
- The migration (`0001_alerts.sql`) and its Drizzle snapshot were
  hand-written rather than generated by `pnpm db:generate` — this sandbox
  could not install `pnpm` (see the PR/issue comment for the exact
  restriction hit). It should be regenerated and diffed against this one
  before merging, or at minimum applied against a real preview database and
  checked, since `pnpm build`/`typecheck`/`lint`/`test` could not be run
  here either.
- The "Occurred at" field on the report form is a plain
  `datetime-local` input with no explicit timezone handling — it's
  interpreted in the server's local timezone. Fine for a single operator
  today; would need fixing before this app has users in more than one
  timezone.
- No e2e coverage was added for the new homepage (the existing Playwright
  smoke test only covers the auth gate) — couldn't run `pnpm test:e2e` here
  to write one with confidence.
